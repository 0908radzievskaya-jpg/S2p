# Почасовой сбор исходных данных из почты

Скрипт читает несколько IMAP-ящиков, обрабатывает только новые письма, сохраняет локальные копии писем и материалов, извлекает текст из вложений и формирует ежедневный Excel-отчет по исходным данным для проектирования.

## Что делает

- подключается к нескольким IMAP-ящикам без изменения статуса писем;
- обрабатывает только новые письма по локальному `state`, а не по флагам на сервере;
- сохраняет `.eml`, текст письма, вложения и скачанные по ссылкам файлы;
- раскладывает материалы по папкам `archive/YYYY-MM-DD/ящик/отправитель/сообщение`;
- дублирует релевантные письма в `sorted_mail/<статус>/YYYY-MM-DD/ящик/отправитель/сообщение`;
- анализирует `pdf`, `docx`, `xlsx`, `html`, `txt`, а также страницы и файлы по ссылкам;
- если в письме есть ссылка на страницу, дополнительно обходит вложенные ссылки внутри этой страницы с ограничением по глубине и скачивает найденные материалы в отдельную подпапку ссылки;
- классифицирует материалы по проектным разделам;
- пополняет ежедневный отчет `reports/report-YYYY-MM-DD.xlsx`;
- оценивает достаточность исходных данных: `достаточно`, `частично достаточно`, `недостаточно`.

## Подготовка

1. Скопируйте `config.example.json` в `config.json`.
2. Заполните параметры IMAP-ящиков.
3. Убедитесь, что доступен Python 3.11+ и установлен `openpyxl`.

Опциональные библиотеки для более качественного разбора:

- `requests`
- `beautifulsoup4`
- `pypdf` или `PyPDF2`

Параметры загрузки ссылок:

- `link_follow_depth` — глубина обхода вложенных ссылок внутри страницы;
- `max_downloaded_files_per_link` — ограничение на число сохраненных файлов по одной исходной ссылке.
- `unprocessed_download_retention_days` — через сколько дней удалять старые скачанные материалы из папки необработанных.

Параметры dashboard:

- `dashboard.host`, `dashboard.port` — где запускать веб-dashboard;
- `dashboard.state_path` — файл, где сохраняются решения менеджера по закупкам;
- `dashboard.file_retention_days` — через сколько дней удалять скачанные файлы для закупок без статуса `Релевантна` или `В работе`;
- `dashboard.file_link_mode` — режим ссылок на файлы: `local` открывает локальный/сетевой путь, `download` отдает файлы и ZIP-папки через серверный `/api/download`;
- `dashboard.min_nmc_rub` — минимальная НМЦК для показа в dashboard, по умолчанию `1500000`. Закупки с распознанной НМЦК ниже порога скрываются, закупки без цены остаются в списке;
- `dashboard.relevant_excel_globs` — Excel-таблицы с AI-релевантными закупками, по умолчанию `reports/Заявки_*.xlsx` и ежедневные `reports/report-*.xlsx`;
- `dashboard.daily_report_exclude_patterns` — дополнительные regex-фильтры для ежедневных отчетов. Встроенный стоп-лист уже убирает рекламу, новости, обучение, банковские гарантии и протоколы итогов;
- `dashboard.local_path_prefix` и `dashboard.network_path_prefix` — замена локального пути на путь на диске `Z:` в ссылках dashboard;
- `dashboard.auth_username`, `dashboard.auth_password` — опциональная Basic Auth для online-размещения. Также можно задать переменные окружения `TENDER_DASHBOARD_USER` и `TENDER_DASHBOARD_PASSWORD`;
- `dashboard.bitrix_webhook_url` — входящий webhook Bitrix24. Если он не задан, статус `Релевантна` сохраняется, но лид и задача не создаются. На сервере webhook и ID пользователей можно хранить в `/etc/tender-dashboard/tender-dashboard.env` или вводить через кнопку `Интеграции`;
- `dashboard.bitrix_gip_user_id` — ID пользователя Bitrix24, которому ставится задача на оценку ГИПу. Если не задан, используется `dashboard.bitrix_task_responsible_id` или `dashboard.bitrix_responsible_id`;
- `dashboard.include_archive_root` — включать ли общий `archive/` в сканирование dashboard. По умолчанию dashboard берет `релевантные/` и глубокие анализы из `reports/analysis_*`.

## Запуск

```powershell
python .\mail_automation.py --config .\config.json
```

Если один из IMAP-серверов отвечает нестабильно, скрипт ограничивает ожидание через `imap_timeout_seconds` в конфиге.

## Dashboard закупок

Dashboard показывает закупки из Excel-таблиц `reports/Заявки_*.xlsx` и ежедневных отчетов `reports/report-*.xlsx`, то есть те, которые AI уже вывел как релевантные. Папки глубокого анализа `reports/analysis_*` используются как дополнительный источник ссылок на материалы для этих строк. Таблица выводит управленческий набор колонок: источник закупки, объект, заказчик, НМЦК, окончание подачи предложений, ТЗ, ссылку на закупку, ТЭП, рекомендацию и папку материалов на диске `Z:`.

В сводке dashboard также показывает, сколько всего входящих источников было проанализировано: общий счетчик берется из `.state/processed_messages.json`, а при синхронизации на VPS передается компактная разбивка по датам в `.state/dashboard_source_counts.json`.

Для каждой строки dashboard добавляет колонку `Краткая аналитическая записка`: она строится по тексту ТЗ/задания на проектирование/ИРД из папок глубокого анализа, включает ТЭПы и основные параметры объекта, выявленные проблемы, неточности и недостающие исходные данные. Если глубокая папка анализа не сопоставлена, в записке явно указано, что нужен прогон исходных файлов через анализатор.

- `Релевантна` — создает входящий лид CRM в Bitrix24 и задачу ГИПу на оценку;
- `Не подходит` — переносит закупку в неподходящие, удаляет переданные файлы на сервере и ставит локальное удаление в очередь ближайшей синхронизации;
- `Подаемся` — переносит закупку в блок `В работе` на dashboard.

При выборе `Релевантна` сервер пытается создать входящий лид в Bitrix24 через `dashboard.bitrix_webhook_url`, затем задачу через `tasks.task.add`. Если webhook или ID ГИПа не настроены, решение сохранится, а в строке появится предупреждение.

Серверные пароли и интеграции можно менять из dashboard кнопкой `Интеграции`. Пустые поля не перезаписывают уже сохраненные значения, а старые секреты не показываются обратно в браузер. Резервная команда на сервере:

```bash
/opt/tender-dashboard/.venv/bin/python /opt/tender-dashboard/tender_dashboard.py configure-secrets --config /opt/tender-dashboard/dashboard.server.json
```

Запуск:

```powershell
python .\tender_dashboard.py serve --config .\config.json
```

После запуска откройте `http://127.0.0.1:8765/`.

Для размещения на сервере используйте отдельный конфиг без IMAP-паролей:

```powershell
Copy-Item .\dashboard.server.example.json .\dashboard.server.json
# В dashboard.server.json задайте dashboard.auth_username/auth_password
.\run_dashboard_server.ps1
```

Серверный конфиг по умолчанию слушает `0.0.0.0:8765` и использует `dashboard.file_link_mode = download`: файлы открываются через браузер, а папки материалов скачиваются ZIP-архивом. Перед публикацией наружу включите Basic Auth или закройте доступ reverse proxy.

Очистка скачанных файлов старше срока хранения выполняется вручную из dashboard или командой:

```powershell
python .\tender_dashboard.py cleanup --config .\config.json
```

Очистка удаляет только файлы из папок скачивания (`downloads`, `downloads_refreshed`, `01_downloaded_docs`) внутри разрешенных корней. Для строк со статусом `Релевантна` или `В работе` файлы не удаляются. Для неподходящих закупок после очистки в dashboard остается компактная строка с названием и датой входа.

## Структура

- `mail_automation.py` — основной скрипт.
- `.state/processed_messages.json` — локальный state уже обработанных писем.
- `archive/` — сохраненные письма и материалы.
- `sorted_mail/` — релевантные письма, разложенные по статусу достаточности.
- `unprocessed/` — временная папка необработанных материалов, из которой старые скачанные файлы можно чистить по сроку хранения.
- `reports/` — ежедневные Excel-отчеты.

## Ограничения

- Для старого бинарного Excel `.xls` скрипт сохраняет файл, но не гарантирует текстовый разбор без дополнительных библиотек.
- Если модуль для чтения PDF не установлен, PDF будет сохранен, а в отчете появится пометка о недоступности извлечения текста.
